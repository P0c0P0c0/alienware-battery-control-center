# Clean-host qualification plan

**Pending execution.** Run only after separate authorization on a disposable installation or spare, supported Alienware host. Use Ubuntu 26.04.1, GNOME Shell 50 and Wayland for comparison with the accepted m15 R7 evidence. A VM without Dell battery sysfs can cover package extraction and compatibility refusal. Use physical hardware for telemetry and performance. Keep the active installation outside this plan.

| Stage | Procedure and acceptance evidence |
| --- | --- |
| Prepare | Use a fresh snapshot, a separate test desktop account, and pre-provisioned dependencies. Record the OS, kernel, model, GNOME version and display server. Verify `dist/SHA256SUMS` and inspect both package control archives. Record that package installation only stages payload files and creates no project services or state. |
| Preflight and activate | Run the administrator and desktop preflights from [INSTALLATION.md](INSTALLATION.md). Test refusal without consent and an occupied target. In a separate authorized run, activate the backend, grant database access only to the test account, and sign in again. Verify the timer, a fresh sample from the disposable test installation, SQLite integrity and the state directory/database permissions. Verify the desktop process has read-only database access and that firmware values stayed unchanged. Activate the dashboard and verify the ten-second startup gate and active GNOME extension. |
| GNOME functional check | Confirm top-right placement, always-on-top, dragging, hide/show, quit/relaunch, opacity and autostart after a fresh login. Verify the SOH/SOC gauges, telemetry and charge thresholds against read-only values. Switch through 24H/7D/30D and check genuine sample points, missing-data states and the two-second clock. Capture a genuine screenshot of the dashboard, crop identifying desktop content, and strip image metadata before retaining it. |
| Performance | Leave the dashboard visible and idle. Run `/usr/bin/python3 -B /usr/share/alienware-battery-control-center-dashboard/dashboard/deploy.py verify`. Retain the 60-second result, backend freshness and service checks. Require CPU strictly below 2% of one logical core, peak sampled RSS strictly below 100 MiB, stable PID and invocation identity, and zero automatic restarts. Record these as widget-process measurements. |
| Upgrade and rollback | On a disposable snapshot, use an explicitly authorized, trusted fixture payload with a harmless program-only change and identical integration files. Upgrade backend and dashboard separately. Check hashes and the verified `.previous` directories, normal activation and preserved SQLite history. Roll back each component and confirm original program hashes, healthy services and retained history. Use a separately approved deterministic startup-failure fixture on the disposable snapshot to exercise automatic restore. Verify service and artifact state after each step. |
| Uninstall | Disable optional notifications for test accounts if enabled. Run each managed uninstaller with explicit consent, then remove the package payloads. Verify project units, launcher, extension and program files are removed as applicable. Check that retained history and the reader group remain, and that unrelated files and settings are unchanged. Restore the disposable snapshot. |

Retain sanitized command results, package hashes, test outcomes and any failure details with the audit record. No clean-host steps were run during local release preparation.
