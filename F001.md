# ABCC-F001 — Dashboard startup readiness

## Observed failure

On a clean GNOME 50 Wayland login, the first GTK compositor connection failed. The dashboard exited with status 1. The unchanged user service waited three seconds, automatically restarted it, and the dashboard became active with `NRestarts=1`. That activation failed the zero-restart acceptance gate.

The dashboard was wanted by the graphical session and ordered after its pre-session target. That ordering did not guarantee an accepting compositor when the first connection ran. The old entry point tried GTK initialization once and immediately exited if there was no default display. The evidence establishes the transient connection failure and retry outcome. It does not distinguish an unavailable socket or compositor from late session environment import.

## Fix and bounds

`dashboard/widget.py` probes GTK immediately. On Wayland, or when the session type is unset, a failed probe is retried within the same process at no more than 250 ms intervals, with an eight-second monotonic retry window. The interval permits immediate start on an already available display and the window covers the observed three-second restart interval with room inside the ten-second service check. Once the default display exists, the code runs the application immediately. Other declared session types retain one-shot behavior. Exhaustion exits 1 with a compositor error, retaining the existing systemd failure handling. The retry window bounds the retry loop. It cannot interrupt a native GTK call blocked in the compositor handshake or repair an incorrect environment inherited at process start.

No polling is added after startup. The unit, hardening, backend, UI, telemetry, firmware readers, ten-second startup gate and sixty-second performance verifier are unchanged.
