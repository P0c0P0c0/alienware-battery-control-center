# ABCC-F001 — Dashboard startup readiness

## Observed failure

On a clean GNOME 50 Wayland login, the first GTK compositor connection failed. The dashboard exited with status 1. The unchanged user service waited three seconds, automatically restarted it, and the dashboard became active with `NRestarts=1`. That activation failed the zero-restart acceptance gate.

The dashboard was wanted by the graphical session and ordered after its pre-session target. That ordering did not guarantee an accepting compositor when the first connection ran. The old entry point tried GTK initialization once and immediately exited if there was no default display. The evidence establishes the transient connection failure and retry outcome. It does not distinguish an unavailable socket or compositor from late session environment import.

## Fix and bounds

`dashboard/widget.py` probes GTK immediately. On Wayland, or when the session type is unset, a failed probe is retried within the same process at no more than 250 ms intervals, with an eight-second monotonic retry window. The interval permits immediate start on an already available display and the window covers the observed three-second restart interval with room inside the ten-second service check. Once the default display exists, the code runs the application immediately. Other declared session types retain one-shot behavior. Exhaustion exits 1 with a compositor error, retaining the existing systemd failure handling. The retry window bounds the retry loop. It cannot interrupt a native GTK call blocked in the compositor handshake or repair an incorrect environment inherited at process start.

No polling is added after startup. The unit, hardening, backend, UI, telemetry, firmware readers, ten-second startup gate and sixty-second performance verifier are unchanged.

## R2 — Native readiness and failed activation

The clean VM invoked autostart, then `Gtk.ApplicationWindow` raised “Gtk couldn't be initialized.” The command reported zero and the service became inactive with no main PID. Zero automatic restarts in that state was a failure. The initial process environment is still unverified. A healthy environment inspected later cannot establish what that first process inherited.

The installed PyGObject 3.56.2 GTK 3 override calls `Gtk.init_check(sys.argv)` at import and caches its result in the override module. The Python window constructor checks that cached flag. A later explicit `Gtk.init_check()` can retry the native display open but does not update the Python flag. Locally, `Gtk.ApplicationWindow.__init__` resolves to the same overridden constructor as `Gtk.Window.__init__`. The override's exact error matches the clean-VM exception. GTK's native readiness and the import-time flag are separate. This explains how the F001 loop could reach activation and then fail at window construction.

R2 opts out of import-time initialization when the public PyGObject switch is available. Explicit readiness requires a successful GTK result and a default GDK display. The native `Gtk.ApplicationWindow.new()` factory avoids the inherited legacy constructor check, including on bindings without the switch. The eight-second startup window is unchanged. Activation exceptions are logged and trigger shutdown. Both the command handler and the application process return failure even if the GI callback trampoline would otherwise report zero.

Six targeted tests and one 41-test offline run passed. The artifacts were independently rebuilt byte-for-byte and checked against their SHA256 manifest. The service unit, hardening, backend and acceptance gates are unchanged. The later user-reported live run satisfied the ten-second autostart gate and the 60-second CPU/RSS limits.
